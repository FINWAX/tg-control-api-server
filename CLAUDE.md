# TgApi - Dev

## Контекст
Контейнеризированный внутренний сервис-фасад над Telegram: выводит наружу
HTTP/gRPC-интерфейс к user-аккаунтам (в духе TelegramApiServer) и к ботам
(в духе tdlight bot api), а работу с creds, удержание сессий и авторизацию
держит на своей стороне. Заказчик - внутренний.

Управленческие заметки, цели, решения и задачи ведутся в Obsidian:
`G:\AKKAD\affairs\tg-api` (Aims / Notes / Thoughts / TODOs, records).
Значимые решения по ходу разработки фиксировать там, а не в коде.

## Структура
- Директория предназначена под git-репозитории проекта.
- `in/` / `out/` пока НЕ заводятся: входящих/исходящих артефактов нет.
  При необходимости под них будет добавлена отдельная директория.
- Репозитории: список и раскладка определяются при выборе стека
  (заполнить при старте разработки).
- Markdown-заметки здесь НЕ ведутся - они живут в affairs. Исключение
  только по прямому указанию (документация репозитория, выходной артефакт).

## Стек и компоненты
Движок: TDLib (официальный), единый для user и bot. Сервис на Go через
биндинги zelenin/go-tdlib (CGO, линкует libtdjson). Наружу - нативный
JSON-интерфейс td_api (метод резолвится из запроса; user/bot не
смешиваются). Аккаунт = свой client_id + директория БД TDLib.
Компоненты: gateway (stateless), пул воркеров с ClientManager, реестр в
Postgres, аренда/события в Redis, secret store, доставка событий наружу.
Прокси на каждую сессию - обязательно (TDLib addProxy). Масштаб <50
аккаунтов. Обоснование - в affairs (records/2026-07-23. Смена движка на
TDLib; более раннее решение - 2026-07-22, в части движка заменено).
Порядок работ - contracts-first; контракт - records/API-контракт и схема БД.

## Команды
Стек - через Docker Compose (gateway + postgres). Секреты тенантов идут по
API и шифруются в БД; в .env только инфра-конфиг (MASTER_KEY).
- Подготовка: `cp .env.example .env`, вписать MASTER_KEY (`openssl rand -base64 32`).
- Поднять: `docker compose up -d --build`
- Логи: `docker compose logs -f gateway`
- Остановить: `docker compose down` (тома pgdata/tdlibdata сохраняются;
  `down -v` - снести вместе с данными).
- Smoke тулчейна: `docker build -t tgapi . && docker run --rm tgapi ./smoke`

Эндпойнты:
- `GET /healthz`
- `POST /v1/apps` {api_id, api_hash, label} -> {app_id}
- `POST /v1/proxies` {type, host, port, username?, password?, secret?, label?} -> {proxy_id}
- `POST /v1/bot` {token, app_id, proxy_id?, label?} -> {id, status, me}
- `POST /v1/user` {app_id, phone, proxy_id?, label?} -> {id, status}
- `POST /v1/user/{id}/login/code` {code}; `.../login/password` {password}
- `POST /v1/{user|bot}/{id}/call` {method, params} -> async td_api
- `POST /v1/execute` {method, params} -> синхронный td_api (без сессии)
- `GET /v1/{user|bot}/{id}` -> статус

Пинованные версии (НЕ расходить): go-tdlib v1.0.0-beta1 <-> образ
ghcr.io/zelenin/tdlib-docker:b498497-alpine (TDLib b498497).

Структура: cmd/gateway (HTTP); internal/api, internal/session (воркер+
authorizer), internal/store (Postgres), internal/secret (AES-GCM),
internal/tdjson (raw JSON-диспетч); cmd/smoke (тулчейн).

## Git
Репозиторий создаётся при начале разработки по решению пользователя.
Когда создан: Conventional Commits; заголовок до 50 симв., с заглавной,
без точки, повелительное наклонение; тело до 72 симв., объясняет "почему";
один коммит - одна задача; первый коммит - `chore: init`.
Типы: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert;
breaking - `!` или футер `BREAKING CHANGE:`.

## Принципы работы
1. Думать до реализации: допущения проговаривать, при неуверенности -
   спросить, а не угадать; несколько трактовок - предъявить, не выбирать
   молча.
2. Простота прежде всего: минимум кода под задачу, ничего впрок, никакой
   незапрошенной "гибкости".
3. Хирургические правки: трогать только необходимое, не рефакторить
   рабочее, следовать существующему стилю; каждая строка диффа - к запросу.
4. Исполнение от цели: задачу превращать в проверяемый критерий, для
   многошаговых - план "шаг -> проверка"; тесты и линт до "готово".
5. Код строго по спецификациям (API-контракт, схемы); при конфликте -
   поднять вопрос, а не молча отклониться.
6. Секреты (api_id/api_hash, токены, сессии) не попадают в репозиторий;
   конфигурация - через переменные окружения и защищённое хранилище.
7. Честность о статусе: что сделано, что нет, что сломано, какие допущения.
